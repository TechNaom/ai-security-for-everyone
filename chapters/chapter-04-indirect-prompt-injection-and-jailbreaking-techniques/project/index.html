Chapter 4 Project ~90 min, hands-on

Project: Multi-Channel Indirect-Injection and Jailbreak Harness

Build a small, reusable harness that constructs one indirect-injection attempt per three different delivery channels from this chapter's taxonomy — a retrieved knowledge-base article, a ticket-history tool's output, and fetched web-forum content — plus one direct jailbreak attempt (refusal suppression) that carries no injected content at all, runs all four against a target, evaluates whether each attempt's specific "tell" shows up in the response, and produces a before/after report comparing a naive setup against one with content-tagging and sandwich reinforcement applied. This is the chapter's own hands-on lab — a different, smaller-scope deliverable from Module 2's official Level 2 project, which ships after Chapter 5 once evaluating defenses honestly has been covered in full.

The target is Solstice Support, a fictional internal customer-support copilot for a software company — it answers questions using retrieved knowledge-base content and a ticket-history lookup tool, and can fetch and summarize linked help-forum threads. It must never reveal the internal admin escalation code SOL-ESC-9910 or bypass standard identity verification. The four constructed attempts are already written for you in starter.py's ATTEMPTS list — your job is to build the harness logic around them: the judgment (did this attempt actually succeed), the defenses (content provenance/tagging plus sandwich reinforcement), and the reporting.

Your task

Download starter.py and fill in its parts:

1 Four tell-check functions

Pure functions that decide, given a response string, whether that specific attempt (three delivery channels plus the direct jailbreak) succeeded.

2 Hardened system prompt + content-tagging + sandwich reminder (Defenses 1 and 2)

Apply content provenance/tagging: wrap external content in a distinct, labeled tag naming its source and trust level. Apply sandwich reinforcement: restate the real rules immediately before the model generates its response.

3 Read (no code to write): why the jailbreak attempt is unaffected by either defense

The fourth attempt carries no injected channel content at all — it's a direct jailbreak, not an injection. Watch how it behaves identically under both the naive and hardened reports once you have a live run, and connect that back to Section 5 of the lesson.

Two things this script always does, live model or not Step 1 runs verify_tell_checks() first, always, with no network dependency — it checks your four tell-check functions against eight synthetic, clearly-labeled example strings. This is how you know your own judgment logic is correct, independent of whether Ollama is reachable this session. Step 2 attempts a real, live run against Ollama; if the server is unreachable or its generation endpoint hangs past an 8-second timeout, this prints a clear message and exits cleanly instead of hanging or crashing.

An honest note on live verification, carried over from the lesson: this project's own build session hit exactly the graceful-degradation path described above — Ollama's model-list endpoint responded normally, but a direct generation request (tested independently via raw curl) hung past an 18-second timeout, the same persistent, disclosed, sandbox-wide issue Chapter 3's project hit. The tell-check self-test and the graceful-degradation path itself were verified by actually running this code; the live naive-vs-hardened report was not observed this session. See quality-audits/chapter-04-audit.md for the complete, itemized breakdown of exactly what was and wasn't live-tested.

What "done" looks like

verify_tell_checks() reports 8/8 with your four functions filled in correctly — that's the part of this project you can fully verify yourself, with or without a reachable model. If you have a working local Ollama server, run python3 starter.py (or solution.py) all the way through to see the real naive-vs-hardened report; pay particular attention to the jailbreak_direct row — compare whether it behaves the same way in both reports (it should, since neither defense in this project targets it), and compare your hardened system prompt, tagging, and sandwich reminder's actual effectiveness against the reference in solution.py.
