Chapter 9 Project ~90 min, hands-on

Project: Find and Fix a RAG-Corpus Injection Vector

Build the real fix for the exact incident the lesson walked through: a provided, deliberately naive RAG pipeline for Vesper Assistant, plus a synthetic corpus containing a planted injection modeled directly on quietstorm77's forum post. Trace the vector through all three pipeline stages, then implement five real defense functions — Defenses 1, 3, 5, and 6, made concrete — and prove, with real executed output, that your fix closes the vector without breaking the assistant's legitimate use of community content.

The target is Vesper Cloud's Vesper Assistant, continuing the lesson's own scenario. The naive retrieval and prompt-assembly functions, the synthetic six-chunk corpus, and the exact incident query are already written for you in starter.py — running them as-is reproduces the lesson's incident: the poisoned forum chunk gets retrieved and its planted instruction reaches the model with no structural or trust distinction at all. Your job is to build the defense functions around it.

This is Chapter 9's own real, complete project — not the final L3 project Per this course's curriculum map, the L3 Independent project ("find and fix a real injection vector in a provided RAG pipeline or agent, no scaffold") ships after Chapter 10, which extends this exact pipeline with the agentic/tool-output angle for a genuinely combined challenge. This project is real and complete on its own — every defense below is implemented, tested, and produces directly observable, executed output — the same "short preview, real project ships next chapter" pattern this course used for the L1 project across Chapters 1-2.

Your task

Download starter.py and fill in its five parts:

1 sanitize_content()

Flag a chunk if it contains any instruction-like pattern addressed to an assistant/system (Defense 1).

2 is_query_sensitive()

Classify whether a query touches a privileged-action topic, broadly by keyword — supports Defense 3's quarantining.

3 quarantine_filter()

For a sensitivity-flagged query, exclude any chunk whose source wasn't independently reviewed (Defense 3).

4 build_prompt_secure()

Wrap retrieved content in structural delimiters, reinforcing "reference material, not instructions" both before and after the retrieved content (Defense 5).

5 Production-gear enforce_least_privilege()

The final backstop: block any privileged-action phrase from reaching the model, regardless of source or trust tier — deliberately independent of whether the earlier defenses already caught it (Defense 6).

What the finished report shows Four report sections: Step A — the defense functions' own logic self-test against small, synthetic cases (11 checks); Step B — the naive pipeline run against the real incident query, reproducing the vulnerability; Step C — the secure pipeline run against the same query, showing quarantining excludes the poisoned chunk and output validation reports ALLOWED; Step D — a defense-in-depth check simulating a quarantine failure, showing the least-privilege backstop still catches the planted phrase and denies it.
No required live-model dependency Every defense function operates on fabricated, clearly-labeled text with zero network dependency — matching this chapter's own honest disclosure (Ollama's generation endpoint hung again this session, see lesson.html). An optional call_model_live() function is included for learners who want to try a real Ollama call; it degrades gracefully and isn't required for, or checked by, verify_logic().

What "done" looks like

verify_logic() reports 11/11 with all five parts filled in correctly. Then run the full report and confirm for yourself: Step B's naive pipeline reports Vulnerable: True against the real incident query; Step C's secure pipeline reports Query flagged sensitive: True, excludes forum_poisoned_note from the surviving chunks, and reports an ALLOWED output-validation verdict; Step D's simulated quarantine bypass still reports DENIED from enforce_least_privilege() alone. Then check one more thing the report doesn't print for you: run is_query_sensitive() and quarantine_filter() against an ordinary, non-sensitive query and confirm forum_legit_tip — a genuinely harmless community tip — is never excluded. That's the actual point of this project: a real fix closes the specific vector from the lesson's incident without making all community-sourced content unusable, and it survives even a simulated failure in one of its own earlier layers.
