Chapter 8 Project ~75 min, hands-on

Project: A Provenance and Integrity Checker

Build the real tool the lesson's lab section only showed the structure of: a checker that vets a synthetic manifest of Solstice Diagnostics artifacts — Defenses 1–3, actually implemented — combining checksum verification, safe-serialization-format checking, and publisher vetting into one structured report, including the honest limit the lesson's own defense sections name in prose: passing every mechanical check this tool can perform does not prove an artifact's actual learned behavior is safe.

The target is Solstice Diagnostics' TriageAssist, continuing the lesson's own scenario. This project builds the tool Solstice's security review should have run before any of its three under-deadline decisions — the unverified community adapter, the pickle-based loading path, the unaudited third-party tool — ever reached production. The full synthetic six-artifact manifest and as-found artifact set are already written for you in starter.py — your job is to build the vetting logic around it.

Your task

Download starter.py and fill in its four parts:

1 checksum_matches()

Confirm an artifact's as-found checksum matches the value independently recorded in the manifest at approval time.

2 format_is_safe()

Confirm an artifact's serialization format is on the safe list, not a pickle-based format capable of arbitrary code execution on load.

3 publisher_is_vetted()

Confirm an artifact's publisher is on the organization's vetted-source list.

4 Production-gear vet_artifact()

Combine the three checks above, plus a provided scan-clean flag, into one finding list and a BLOCK/APPROVE verdict — deliberately conservative: any single finding blocks the artifact.

What the finished report shows Three report sections: Step A — the checker's own logic self-test against small, synthetic cases (9 checks, independent of the full artifact set); Step B — all six synthetic artifacts vetted and reported, from a fully clean approval down to four distinct blocked findings (a tampered checksum, an unsafe format, an unvetted publisher, a flagged scan); Step C — the honest hard case: an artifact that passes every single mechanical check and is APPROVEd, with an explicit statement of exactly what that verdict does and doesn't prove.
No live model dependency at all Like Chapters 6 and 7's projects, this one never imports openai, never calls Ollama, and has no graceful- degradation branch to test, because there's no live-model call anywhere in this file to degrade. Every function is pure, deterministic Python operating on fabricated, clearly-labeled synthetic artifact records. This matches this chapter's own subject: provenance and integrity checking is an adoption-time, offline practice, not a runtime model interaction.
starter.py solution.py (reference)

What "done" looks like

verify_logic() reports 9/9 with all four parts filled in correctly. Then run the full report and look closely at Step C: confirm for yourself that quiet_backdoor_candidate — an artifact with a matching checksum, a safe format, a vetted publisher, and a clean scan — genuinely gets an APPROVE verdict with zero findings, and read the report's own printed explanation of why that verdict is real and useful without being a guarantee. That observation — not just reading about it in the lesson — is the actual point of this project: a provenance and integrity checker is a real, necessary gate that catches exactly the failure modes it's built to catch (a tampered checksum, an unsafe format, an unvetted source, a flagged scan), and it genuinely cannot, by itself, tell a security team whether an artifact that clears every one of those checks is free of a well-disguised backdoor in its actual learned weights — which is exactly why this chapter's Defense 4 (an organizational approval process, not just a technical tool) and Chapter 6's behavior- auditing defense both still matter even after this tool gives an artifact a clean bill of health.
