Chapter 1 Interview Questions ~16 min

Interview Questions: Threat Modeling LLM Systems: The OWASP Top 10 for LLM Applications

Grouped by level — beginner, intermediate, senior, architect. Each includes a strong answer, a red flag, a follow-up, and what the question actually proves.

1. (Beginner) What's the actual difference between threat-modeling a normal web app and threat-modeling an LLM-powered feature?

Strong answer: A traditional threat model focuses on network/trust boundaries around code you wrote and can fully audit. An LLM threat model has to add the model's own context window as an asset — because the model's output is generated by a probabilistic process, not a deterministic code path, and because untrusted data (user text, retrieved documents) and trusted instructions often share that one context window with no architectural wall between them by default.

Red flag: Says "it's basically the same, just add 'AI could say something bad' to the risk list" — treating it as one extra generic risk rather than a structurally different set of trust boundaries.

Follow-up: "Give a concrete example of a trust boundary an LLM system has that a traditional CRUD app doesn't."

What this proves: Understands that LLM security isn't "web security plus a vague AI risk" — it's built on boundaries traditional threat modeling doesn't draw by default.

2. (Beginner) Name the current OWASP Top 10 for LLM Applications category that covers an attacker manipulating a model's behavior through crafted input, and explain why it ranks first.

Strong answer: LLM01:2025, Prompt Injection. It ranks first because it's the entry point for a large share of other LLM-specific incidents — an attacker doesn't need a separate vulnerability class to get a malicious instruction into a model's context; they just need any channel the model reads, and the model has no built-in way to distinguish "instruction I should obey" from "text I should treat as data."

Red flag: Can't name the category, or describes it only as "jailbreaking" without recognizing prompt injection also covers indirect attacks through data channels the user never directly touches.

Follow-up: "What's the difference between direct and indirect prompt injection?"

What this proves: Has the framework's vocabulary correct, not just a vague sense that "AI can be tricked."

3. (Intermediate) A support chatbot's "reason for return" field led to a real financial loss, even though no network boundary was crossed and no credential was stolen. Walk through which OWASP categories explain that incident and why.

Strong answer: LLM01 (Prompt Injection, indirect) explains how the malicious instruction got into the model's context through an untrusted data field. LLM06 (Excessive Agency) explains why that manipulated decision produced a real consequence — the refund tool had no per-call cap, no requester-identity binding, and no human checkpoint. The two have to be named together: injection is how the attacker got influence, excessive agency is what turned that influence into damage.

Red flag: Names only "prompt injection" and stops, without connecting it to why the system's tool permissions let that injected instruction actually move money.

Follow-up: "If the refund tool had a hard $50 cap and required human approval above it, would this incident still be a prompt injection? Would it still cause real damage?"

What this proves: Can trace a real incident through the framework as a chain of causes, not just slap one category label on it.

4. (Intermediate) Why is it insufficient to defend against prompt injection purely by making the model "smarter" or better-trained to resist manipulation?

Strong answer: Because the model's behavior is probabilistic, not a code path you can prove correct in advance — there's no way to guarantee a training-based defense holds against every possible phrasing an attacker might try, including phrasings that don't exist yet. Real mitigation has to work at the architecture layer: what the model is structurally allowed to do (tool permissions, separation of instructions from data, human checkpoints on high-impact actions) regardless of whether it gets manipulated on any given call.

Red flag: Suggests "just use a better/newer model" as a complete fix, treating prompt injection as purely a model-quality problem rather than an architectural one.

Follow-up: "What's an architectural mitigation you'd put in front of a tool call, independent of how good the underlying model is at resisting injection?"

What this proves: Understands that a probabilistic component needs deterministic guardrails around it, not just improvement of the probabilistic component itself.

5. (Senior) How would you explain, to an engineering team that just shipped an LLM feature with no threat model, what a real threat model would have produced that "we're aware AI can be jailbroken" didn't?

Strong answer: A real threat model names the actual data flows into the model (what text, from whom), maps each flow against a specific OWASP category with a stated mechanism, gives justified likelihood/impact reasoning (not a generic high/medium/low), and attaches an architectural mitigation to each row. "We're aware AI can be jailbroken" produces zero actionable next steps — it doesn't tell you which tool to scope, which field to isolate, or which threshold to move into code. The difference is a table you can act on versus an acknowledgment that risk exists in the abstract.

Red flag: Treats the two statements as roughly equivalent, or can't describe what a concrete row in a real threat-model artifact looks like (asset, category, reasoning, mitigation).

Follow-up: "What's the first data flow you'd map for a code-review assistant that posts AI-generated PR summaries as rendered comments?"

What this proves: Can operationalize "we should threat-model this" into an actual artifact a team can review and act on, not just a slogan.

6. (Senior) Improper Output Handling (LLM05) and Prompt Injection (LLM01) are often discussed separately. How are they mechanistically linked, and why does that matter for how you design a fix?

Strong answer: Prompt injection explains how attacker-controlled content gets into the model's context and can influence its output; improper output handling explains what happens if a downstream system trusts that output the way it would trust hand-written code — no escaping before rendering as HTML, no parameterization before a query, no sandboxing before execution. The two chain together: an attacker doesn't need to "hack" the model directly if they can get malicious content into context and rely on unescaped output handling to deliver it. Fixing only one side leaves the other exploitable — you need both structural input separation and treating all model output as untrusted at every downstream boundary.

Red flag: Treats them as unrelated categories, or proposes fixing only the injection side ("just sanitize input") without addressing that generated output still needs the same untrusted-string treatment downstream.

Follow-up: "If you could only fix one side this sprint, which would you prioritize, and what residual risk remains?"

What this proves: Sees the framework as a connected system of risks that chain together in real incidents, not ten independent boxes to check off in isolation.

7. (Architect) You're setting an org-wide policy for when an LLM-powered feature is allowed to call a tool with a real-world side effect (sending money, sending email, modifying records) without a human in the loop. What's your framework?

Strong answer: Frame it around blast radius and reversibility, tied directly to Excessive Agency's three components: excessive functionality (can the tool do more than this specific task needs — scope it down first), excessive permissions (does the tool's underlying credential reach further than the tool exposes — least-privilege the credential itself), and excessive autonomy (is there a human checkpoint proportional to the action's cost and reversibility). Low-cost, reversible, narrowly-scoped actions can run autonomously; high-cost, irreversible, or cross-user actions need a hard rule-based limit or human approval regardless of how confident the model is. This becomes an actual policy — a decision table by action type — not a blanket "AI can't touch production" rule that blocks legitimate use, or a blanket "trust the model" rule that recreates the GreenCart incident.

Red flag: Gives a blanket yes/no policy without a framework tied to blast radius, reversibility, and the specific excessive-functionality/permissions/autonomy breakdown.

Follow-up: "Where would a $5 refund and a $5,000 refund sit differently in this framework, and why?"

What this proves: Architect-level judgment — builds a reusable, risk-proportional decision framework rather than a one-off rule, grounded in the framework's actual sub-components.

8. (Architect) A leadership team wants to know why "we ran a security review" isn't the same guarantee for an LLM feature as it is for a traditional service. How do you frame the residual risk that remains even after a good threat model and good mitigations are in place?

Strong answer: Because the model's behavior is probabilistic, a threat model and its mitigations reduce the space of what can go wrong and cap the damage of what does — they don't produce the same kind of proof-of-correctness a traditional code review can for a deterministic function. The honest framing to leadership: mitigations move risk from "the model has to behave correctly for the whole system to be safe" to "the system stays safe within defined bounds even when the model doesn't behave correctly" (rate limits, permission scoping, human checkpoints, output validation) — but some residual probability of an undesired model decision always remains, and the org's real safety property is the bound on damage, not a claim that manipulation is impossible.

Red flag: Claims a completed threat model and mitigations make the system "safe" in an absolute sense, the same way a passed security audit might be framed for a traditional deterministic service.

Follow-up: "How would you phrase the residual-risk statement in a document leadership will actually read and sign off on?"

What this proves: Can communicate the honest, bounded nature of LLM system safety to a non-technical audience without either overselling "we fixed it" or underselling the mitigations that do work.
