Project Preview: Threat-Model a Real LLM Feature End to End

This chapter doesn't ship its own project. Module 1's Level 1 (Guided) project needs the full framework this chapter introduces plus the applied practice Chapter 2 builds on top of it, so it unlocks once Chapter 2 is done.

Handing you a real feature to threat-model before you've walked the OWASP Top 10 end to end against a worked example (this chapter's GreenCart/Aurora walkthrough) would turn the project into guesswork instead of applied judgment. Rather than pad this page with a placeholder exercise, here's what's actually coming.

What the L1 project will ask you to do

The Level 1, Guided project (per the course's curriculum map) hands you a real, given LLM feature and asks you to threat-model it end to end: map the assets and data flows, run every one of them against the OWASP Top 10 for LLM Applications the way the GreenCart walkthrough in this chapter did, justify a real likelihood/impact reasoning for each finding, and attach an architectural mitigation to every row — not a hope that the model behaves.

Everything in this chapter — the framework itself, the walkthrough method, the distinction between a trust boundary a network diagram draws and one only an LLM threat model draws — is the foundation that project leans on directly.

Where this fits Module 1 — Threat Modeling LLM Systems: Chapter 1 (this chapter) builds the OWASP Top 10 framework and the walkthrough method against a worked example, and Chapter 2 applies it to a real, given LLM feature. The project ships once both are in place.

Why waiting matters

A project that asked you to "just threat-model something" right now would produce the exact failure mode this chapter opens with: a vague "AI can be hacked" risk rating with no actionable next step. Building the framework and walking it against one real example first means the project actually tests whether you can run the checklist yourself, not whether you can guess.
