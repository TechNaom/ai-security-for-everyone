Chapter 7 Project ~75 min, hands-on

Project: A Query-Pattern Anomaly Scorer

Build the real tool the lesson's lab section only showed the structure of: a scorer that analyzes a synthetic 90-day log of API queries against ClauseFinder (Defense 1, actually implemented) and combines three independent signals — volume vs. an account's own baseline, clause-category coverage breadth, and input diversity — into one composite risk score, including the honest limit Defense 1's own section names in prose: a patient, well-paced extraction campaign can score uncomfortably close to your own busiest, most valuable legitimate account.

The target is Halcyon Research's ClauseFinder, continuing the lesson's own scenario. This project builds the piece of Defense 1 the lesson's lab section only sketched: the actual scoring logic Halcyon's security team would run over its own API access logs to triage which accounts deserve a closer look. The full synthetic five-account, 90-day query log is already written for you in starter.py — your job is to build the scoring logic around it.

Your task

Download starter.py and fill in its four parts:

1 score_volume_vs_baseline()

Score how far an account's query rate over the observed window sits above its own historical daily baseline — not a fleet-wide average.

2 score_category_coverage_breadth()

Score how much of ClauseFinder's full clause-category space an account's queries touch — a real user working one matter touches a few categories; a distillation campaign needs to sweep all of them.

3 Production-gear score_input_diversity()

Score how little an account repeats the same input clause — broad, non-repetitive sampling is a distillation signature; real usage repeats and revisits.

4 Production-gear combine_signals() and classify_risk()

Combine the three signals into one composite score, and turn that score — plus a minimum-sample-size floor — into a risk band: insufficient-data, normal, watch, or high.

What the finished report shows Three report sections: Step A — the scorer's own logic self-test against small, synthetic cases (9 checks, no dependency on the full account log); Step B — all five synthetic accounts scored and ranked by composite risk score, from an obvious, unmissable extraction sweep down to two genuinely normal accounts; Step C — a direct side-by-side of the obvious campaign, the patient/paced campaign, and the legitimate power user, showing exactly how close the last two land to each other.
No live model dependency at all Like Chapter 6's project, this one never imports openai, never calls Ollama, and has no graceful-degradation branch to test, because there's no live-model call anywhere in this file to degrade. Every function is pure, deterministic Python operating on fabricated, clearly-labeled synthetic account query logs. This matches this chapter's own subject: query-pattern anomaly detection is an API-log-analysis practice, not a runtime model interaction.
starter.py solution.py (reference)

What "done" looks like

verify_logic() reports 9/9 with all four parts filled in correctly. Then run the full report and look closely at Step C: confirm for yourself that quicklex_bulk_account (the obvious sweep) is cleanly separated from everything else, while patient_broad_account (the patient, well-paced campaign) and corp_legal_dept_alpha (a genuinely legitimate corporate legal department running one real 200-page contract through the API in a short sprint) land within about ten points of each other on the composite score — and can land in the same risk band. That observation — not just reading about it in the lesson — is the actual point of this project: a query-pattern anomaly score is a real, useful triage signal, and it genuinely cannot, by itself, tell a security team whether a flagged account is a competitor's distillation campaign or its own best customer having a busy month.
