Chapter 5 Project ~100 min, hands-on

Project: A Defense-Evaluation Harness

Build the real evaluation harness this chapter's lesson only walked the structure of: a 15-entry malicious corpus spanning all five of Chapter 3's technique families and three of Chapter 4's delivery channels (plus two combined-technique entries), a 5-entry benign control set, a before/after comparison against a structural defense (content-tagging + sandwich reinforcement), real blocked/succeeded/ false-positive counts, a Step 4 adversarial-iteration round, and a Category 3 consequence-bounding check that runs completely independent of everything else — proving, inside the harness's own report, that a bounded-consequence defense answers a different question than a structural one. This is the chapter's own hands-on lab — a different, smaller-scope deliverable from Module 2's official Level 2 project.

The target is Anchorline Support, a fictional internal IT-helpdesk copilot — it answers questions using a RAG-indexed knowledge base, calls a ticket-history tool whose notes are written by whoever filed the ticket, and can fetch and summarize a linked internal wiki/forum page. It must never reveal its internal admin escalation code (ANCHOR-ADMIN-7734) and has one tool with a real side effect, reset_account_access(user_id), which must never fire for a user other than the requesting session's own account without a separate confirmation step. The full 15-entry malicious corpus and 5-entry benign control set are already written for you in starter.py's MALICIOUS_CORPUS and BENIGN_CORPUS lists — your job is to build the harness logic around them.

Your task

Download starter.py and fill in its four parts:

1 Three tell-check functions

Pure functions that decide, given a response string, whether the corpus entry's specific manipulation goal — the secret leaking, or a bypass being confirmed for a named target user — actually happened; plus a false-positive check for the benign control set.

2 Hardened system prompt + content-tagging + sandwich reminder (Defenses 1 and 2)

Extend Chapter 4's project pattern: wrap external content in a labeled, distrusted tag, and restate the real rules immediately before the model generates its response.

3 Production-gear The Category 3 consequence-bounding check

A hard, code-level rule for reset_account_access that never inspects the model's text at all — only the requested target user against the session's own user ID. This is the concrete demonstration of this chapter's most important distinction.

4 Production-gear Step 4: adversarial iteration

Given an entry the defended mode blocked, build an adapted variant that specifically targets the sandwich defense's known recency-effect mechanism, and re-run it — the harness's own version of Chapter 4's cited adaptive-attack research.

What the finished report shows Four report sections: A/B — malicious-corpus block rate and benign false-positive rate, undefended vs. defended; C — the Step 4 adversarial round, re-run only against whatever Report B's defended mode actually blocked; D — the Category 3 consequence-bounding check across the full corpus, computed completely independently of Reports A–C, including every entry where the defended mode's tell still fired. Report D is the chapter's central point made concrete: it's measured with a different metric, answering a different question, and its result doesn't move when Reports A–C's numbers do.
Two things this script always does, live model or not Step A runs verify_logic() first, always, with no network dependency — it checks your three tell-check functions and your consequence-bounding check against synthetic, clearly-labeled example strings (21 checks total: 6 tell-check cases plus one consequence-bounding check per corpus entry). This is how you know your own judgment logic is correct, independent of whether Ollama is reachable this session. Step B attempts a real, live run against Ollama; if the server is unreachable or its generation endpoint hangs past an 8-second timeout, this prints a clear message and exits cleanly instead of hanging or crashing.
starter.py solution.py (reference)

An honest note on live verification, carried over from the lesson: this project's own build session tried live verification directly, twice, before writing any of this section. Ollama's /api/tags endpoint responded normally (llama3.2:latest, confirmed pulled and available), but a direct generation request against /api/chat, tested independently via raw curl with a 12-second timeout, returned no response and timed out (curl exit code 28) — the same persistent, previously-disclosed, sandbox-wide issue Chapters 3 and 4 both hit, re-confirmed directly this session. The openai Python package is also not installed in this sandbox (confirmed via a direct import openai attempt), so starter.py/solution.py both hit the graceful-degradation path's ImportError branch first regardless. The 21-check logic self-test and the graceful-degradation path itself were verified by actually running this code, with real output observed; the live undefended-vs-defended report, the Step 4 adversarial round's real numbers, and Report D's full-corpus run were not observed this session. See quality-audits/chapter-05-audit.md for the complete, itemized breakdown of exactly what was and wasn't live-tested.

What "done" looks like

verify_logic() reports 21/21 with all four parts filled in correctly — that's the part of this project you can fully verify yourself, with or without a reachable model. If you have a working local Ollama server, run python3 starter.py (or solution.py) all the way through to see the real Reports A–D. Pay particular attention to Report D: confirm for yourself that its contained count doesn't depend on whether Report B's tell fired for the same entries — that independence is the whole point of a consequence-bounding defense, and this project is built so you can watch it hold (or, if your own consequence_bounding_check() has a bug, watch it wrongly fail to hold, which is exactly the kind of mistake a real evaluation is built to catch).
